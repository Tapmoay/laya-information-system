# 适配指南：换一个环境、换一个用户时怎么做

> 这份技能是**"怎么做"的说明**，不是必须逐字执行的脚本。
> 你的环境很可能和作者不同：没有 GPU、没有聊天渠道、目标完全不同、推送入口也不同。
> 先读这一页，再决定哪些照抄、哪些替换。
>
> 一句话：**不变量照抄，实现随便换，判断结果不要照抄。**

## 0. 先问三个问题（不要替用户假设）

1. **你有这套系统的仓库吗？** 有 `tools/`、`judgment/`、`config/` 才能执行完整链路；
   只有这份技能时，你拿到的是方法与契约，需要自己实现或找作者要仓库。
2. **用户要什么？** 长期目标、当前任务、探索方向——用他的，不要用作者的。
   作者的 37 个来源、阈值、示例读物都只是参考实现。
3. **结果送到哪？** 邮箱、文件、企业微信、Telegram、Slack……**由用户决定**。
   本技能只规定适配器契约，不规定必须用哪个渠道。

## 1. 不变量（这五条不能改）

1. **测量不等于决策。** 模型只产出测量记录；选择由确定性规则做，终选由 agent 做。
2. **未知必须可表达。** 调用失败记 failure，正文为空记 unscorable；
   不许把"没判断"写成 0 分，也不许把"不知道"当成"很旧/很新"。
3. **理由必须指向"它能帮我做什么"。** 说不出具体动作/判断/设计的，不算理由；
   允许少于上限，不许凑数。
4. **推送幂等，失败不记账。** 只对真正送达的条目落 7 天窗口；发失败的下次补发。
5. **改配置/参数之前先向用户解释。** 改什么、为什么、影响什么；解释完再执行并留痕。

违反任何一条，实现得再漂亮也不算这套系统。

## 2. 可以替换的部件

| 部件 | 作者的实现 | 你可以换成 | 必须保留什么 |
|---|---|---|---|
| 需求 | `demand/demand-*.json` | 数据库、表单、对话记录 | 四类信息：目标/任务/探索/预算 |
| 来源 | 37 个登记源 | 你所在领域的源 | 每条内容的取证链（从哪来、何时抓、原文） |
| 测量 | 本地 decider / DeepSeek API | 任何能输出 13 个分数的模型 | 分数范围、形态权重、失败语义 |
| 打分 | `judgment/scoring.py` | 你自己的确定性公式 | 可复算、可解释、阈值不手改 |
| 终选 | `agent/AGENT.md` | 你的验收标准 | 理由 + 逐字证据 + 容量上限 |
| 推送 | 邮箱 / 文件 | 企业微信、Telegram、Slack… | dry-run、item_id 记账、失败不记账 |
| 存储 | `runs/`、`store/*.jsonl` | SQLite、对象存储 | 可回看、可对账 |
| 调度 | Windows 任务计划 | cron、systemd、云函数 | 失败有日志、失败有通知 |

## 3. 推送入口：由用户决定，按契约适配

**不要默认某个渠道。** 先问用户："你平时在哪里看？邮件、文件、企业微信，还是只要文件？"
推荐的上线顺序：

1. `file`：只落文件，不发送、不记账——先验证产物；
2. `email`：一封邮件，最容易跨环境；
3. 企业微信 / Telegram / 其他：需要凭据，最后接；
4. `none`：只生成不打扰。

### 适配器契约（加新渠道时照这个写）

```text
prepare(entries) -> payload         # 不发网络
send(payload, dry_run) -> sent_ids  # dry_run 只打印
ledger(sent_ids)                    # 只对成功送达的 item_id 落账
```

必须满足：

- `dry_run` 不发送、不记账；
- 失败返回空集合并给出可读错误，**不把失败条目写进台账**；
- 一条发送失败不影响其余条目（能拆条就拆条）；
- 凭据只从环境变量/凭据文件读，不写进配置；
- 同一份内容重跑，不会产生第二条推送（幂等键或台账）。

如果用户的渠道不在本技能里：在 `tools/push.py` 加一个分支，或在你的实现里加一个适配器。
**不要改判断层来迁就渠道。**

## 4. 判断 provider：先看环境，再看用户偏好

```text
有本地权重 + 可用 GPU？ ──是──▶ local（免费、离线、慢）
        │否
有 DEEPSEEK_API_KEY？ ──是──▶ cloud（快、按 token 计费）
        │否
问用户：要下载权重，还是申请 key？ ── 都没有 ──▶ 先别跑测量
```

`auto` 只按"有没有本地权重"决定，不猜速度；两者都没有时**拒绝启动**，不要偷偷降级成空分。

**换 provider 之前**：先跑 30–50 条对照，看候选池重合与 top-K 重合；
阈值不随 provider 自动迁移。对照方法与实测见 `docs/39-judge-comparison.md`。

## 5. 从零实现的最小顺序（没有仓库时）

| 步 | 做什么 | 验收 |
|---|---|---|
| 1 | 写需求：目标/任务/探索/预算 | 用户能读回并确认 |
| 2 | 抓取/接入：至少 3 个源，带取证链 | 每条能回答"从哪来、何时抓" |
| 3 | 测量：13 个问题（4 方向 + 5 价值 + 2 质量 + 形态 + 招募） | 输出分数与形态；失败/不可判显式 |
| 4 | 确定性打分：价值取最高、质量取平均、形态降权、过时降权 | 同输入同输出，可复算 |
| 5 | 终选：Agent 从候选池挑 ≤5+≤2，写理由 + 逐字证据 | 校验器能拒绝空理由/假证据 |
| 6 | 交付：标题 + 摘要 + 原文链接 + 通道 | 用户能点开原文 |
| 7 | 台账：推过的 7 天内不再推 | 重跑不会重复 |

缺任何一步，先补那一步，不要用"先跑起来"掩盖。

## 6. 测试阶梯（别一上来就全量）

1. `--dry-run`：看提示词/消息/邮件，不发网络；
2. `file` 渠道：只落文件，确认产物结构；
3. 1 条真实内容：测量 → 打分 → 终选 → 推送全链路；
4. 10 条：看失败率、覆盖、延迟；
5. 全量：加台账与回滚。

每一步的通过标准：**产物存在 + 覆盖可解释 + 失败有记录**。
其中"失败有记录"比"成功"更重要——无人值守最坏的失败是"看起来跑了，其实没发"。

## 7. 不要照抄的东西

- 作者的 37 个来源、域名、代理地址；
- 作者的阈值（0.45）与权重——它们是对作者语料与 provider 标定的；
- 作者的长期目标、当前任务、示例读物；
- 作者的 SMTP 授权码、聊天工具凭据；
- 作者的 `runs/` 与 `store/` 历史（含已推送台账）。

照抄这些，得到的不是"你的信息环境"，而是"作者的旧读物"。

## 8. 交付前确认清单

- [ ] 六个问题已回答并写进初始文档；
- [ ] 用户读回了目标/任务/探索，确认没有替他编；
- [ ] 判断 provider 与推送渠道是用户选的，不是默认的；
- [ ] 第一次跑用 `file` 渠道，用户看过产物；
- [ ] 失败路径测过：拿掉 key/断网/空正文，系统说的是"失败"而不是"0 分"；
- [ ] 台账对得上：发了几条就记几条；
- [ ] 改配置的规矩已经告诉用户（先解释、`--why`、变更记录）。
