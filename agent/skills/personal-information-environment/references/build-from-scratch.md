# 从零构建：把方法变成一套能跑的系统

> 这份文件回答一个问题：**如果只有技能包、没有仓库，AI 该怎么把整个系统搭起来？**
> 有仓库时先看 §0：多数情况下你不需要重写，只需要读懂并改配置。

## 0. 先选一条路

| | A. 用仓库（推荐） | B. 从零构建 |
|---|---|---|
| 适合 | 你拿到了代码 | 没有代码、要换技术栈、或要理解每一步为什么存在 |
| 成本 | 装依赖、配 key/权重、改配置 | 每个阶段自己实现；约几天到几周 |
| 风险 | 低 | 容易漏掉"失败语义"和"台账" |

**判断标准**：能拿到 `tools/`、`judgment/`、`contracts/` 就不要重写。
重写只在这三种情况下合理：换语言/框架、换领域且现有源完全不可用、教学/研究。

## 1. 最小闭环

```text
需求快照 → 来源登记 → 抓取/取证 → 规范化/去重
   → 13 问测量 → 确定性打分 → 候选池 → Agent 终选
   → 交付 → 台账 → 反馈/参数
```

每一步的产物是下一步的输入。**没有产物就不算完成**，不要用"跑通了"代替"产物存在"。

## 2. 六个不可省的契约

| 对象 | 最小字段 | 谁写 | 失败怎么表达 |
|---|---|---|---|
| DemandSnapshot | 目标、当前任务、探索方向、约束 | 用户/配置 | `state.status != OK` 时停止测量 |
| CandidateRecord | `item_id`、标题、URL、正文、语言、取证链 | 抓取层 | 抓取失败写 `reason_code`，不写空正文 |
| MeasurementRecord | 12 个 0–1 分 + 形态权重 + provider/revision | 模型适配器 | `ERROR`/`ABSTAIN`，**不是 0 分** |
| ScoreRow | 合成分、各分量、参数版本 | 确定性代码 | 缺测量就不打分，不猜 |
| SelectionDecision | picks（core/exploration）、excludes、理由、逐字证据、容量 | Agent | 校验不过拒绝落盘 |
| DeliveryStatus | 渠道、`item_id`、送达时间 | 交付层 | 失败不记账；重试幂等 |

最小 JSON 形状：

```json
{"demand_snapshot_id":"demand-...","active_goals":[{"statement":"..."}],
 "active_tasks":[{"statement":"...","status":"ACTIVE"}],
 "exploration_intent":{"enabled":true,"domains_hint":["..."]},"state":{"status":"OK"}}
```

```json
{"item_id":"item-...","title":"...","canonical_url":"https://...",
 "text_clean":"...","detected_language":"en",
 "provenance":{"index_url":"...","index_fetched_at":"...","matched_rule":"...","http_status":200}}
```

```json
{"item_id":"item-...","scores":{"primary":{"noul":0.42},"form":{"probabilities":{"TECHNICAL":0.8}}},
 "judge":{"provider":"cloud","model":"...","attempts":1,"usage":{"prompt_tokens":1}}}
```

```json
{"picks":[{"item_id":"...","slot":"core","reason":"...","evidence":"摘要原文"}],
 "excludes":[{"item_id":"...","reason":"...","evidence":"摘要原文"}]}
```

## 3. 七个构建阶段

### S1 需求快照

- **做什么**：问用户六个问题（目标/任务/探索/判断方式/推送方式/时间），写一份 JSON；
- **最小实现**：一个表单或 CLI，写 `demand/demand-<日期>.json`；
- **验收**：四个方向槽都能从文件里读出来；缺槽时用 fallback，不增加问题数；
- **失败**：没有需求就停止，不要抓取。

### S2 来源与抓取

- **做什么**：登记"列表页 + 路径正则 + 允许的主机"；抓列表、发现链接、抓正文；
- **最小实现**：3 个源即可；每个 item 记录列表页、抓取时间、匹配规则、最终地址、HTTP 状态；
- **验收**：每条内容都能回答"从哪来、何时抓、按什么规则命中"；
- **失败**：robots/付费墙/超时分别有原因码；不要绕过对方意愿。

### S3 规范化与去重

- **做什么**：去导航、编码嗅探、正文截断（固定长度）、URL 规范化；
- **去重三层**：URL → 内容摘要 → 事件锚点（跨源才合并事件，同源近似是连载）；
- **验收**：同一条内容重复抓取只留一条；不同事件不会被误并；
- **失败**：拿不到正文的条目标记 `unscorable`，不要送测量。

### S4 13 问测量

- **问句**：4 方向 + 5 价值 + 2 质量 + 形态 + 招募；问句从需求槽取值；
- **最小实现**：
  - 本地：一个能对 13 个问题给出 0–1 分的模型；
  - 云端：一次 JSON 调用（见 `cloud-judgment.md` 的 schema 与解析规则）；
- **验收**：同一输入可复算；分数在 [0,1]；形态权重归一化；失败显式；
- **失败**：失败/不可判分别落盘；**绝不写 0 分**。

### S5 确定性打分

- **做什么**：方向门槛 → 价值取最高 → 质量取平均 → 形态降权 → 过时降权；
- **最小实现**：一个纯函数，输入测量与参数版本，输出分数与分量；
- **验收**：同输入同输出；参数有版本号；阈值可回滚；
- **失败**：缺测量不打分；不要用模型补分数。

### S6 候选池与终选

- **做什么**：按分数排候选（加每源上限、事件/视觉席位），把候选摘要给 Agent；
- **终选规则**：核心 ≤5、探索 ≤2；每条理由 + 从摘要里逐字摘的证据；
- **验收**：校验器能拒绝空理由、假证据、超容量、候选池外条目；
- **失败**：宁可少于上限；不要为了凑数加条目。

### S7 交付、台账、调度

- **做什么**：把选中条目渲染成最终读物；送到用户选的渠道；只对成功送达的记账；
- **最小实现**：file 渠道先跑通，再加 email/其他；
- **验收**：重跑不重复推送；失败不占 7 天窗口；dry-run 不发送；
- **失败**：失败留日志；不要静默什么都不发。

## 4. 五条不能改的不变量

1. 测量不等于决策；
2. 未知必须可表达（`UNKNOWN` / `ERROR` / `unscorable` 分开）；
3. 理由必须指向"它能帮我做什么"，证据必须逐字；
4. 推送幂等，失败不记账；
5. 改配置/参数前先解释。

违反任何一条，实现得再漂亮也不是这套系统。

## 5. 测试阶梯

1. **单条**：一条真实内容走完 S2–S6，产物齐全；
2. **十条**：看失败率、去重、候选池；
3. **一百条**：看时间/成本、覆盖、台账；
4. **故障注入**：拿掉 key、断网、空正文、坏 JSON——系统必须说"失败"而不是"0 分"；
5. **重放**：同一批跑两次，第二次不重复推送；
6. **调度**：定时触发一次，产物与日志可对账。

每一步的通过标准：**产物存在 + 覆盖可解释 + 失败有记录**。

## 7. 不要先做的

- 不要先做 UI、多用户、权限、向量数据库；
- 不要让模型直接决定推荐；
- 不要在没有需求快照时抓取；
- 不要把失败写成 0 分；
- 不要在没有台账时推送；
- 不要照抄别人的阈值——它对应另一套语料与 provider。

## 8. 完成定义（DoD）

- [ ] 六个问题有答案，需求快照存在且 `state.status == OK`；
- [ ] 至少 3 个源，每条内容有取证链；
- [ ] 13 问能跑，失败/不可判显式；
- [ ] 打分是确定性函数，参数有版本；
- [ ] 终选有理由 + 逐字证据，容量受限；
- [ ] 至少一个渠道可 dry-run 与真发；
- [ ] 台账只记成功，重跑不重复；
- [ ] 故障注入测试通过；
- [ ] 一次定时运行可对账。

## 9. 给 AI 的最短执行顺序

1. 读 `MISSION.md` 与用户的 `information-policy.md`；
2. 问六个问题，写需求快照；
3. 选 3 个源，实现抓取与取证；
4. 实现 13 问测量（先本地或云端一条路）；
5. 写确定性打分；
6. 让 Agent 按 5+2 终选，加校验；
7. 先做 file 渠道，再加真实渠道；
8. 加台账、dry-run、失败注入；
9. 最后才接定时与通知。

**一句话**：先让一条内容走完全程，再谈规模和自动化。
