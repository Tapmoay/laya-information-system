# 29 · 去重与时效：别让我第二次看见同一条

> 这份文件回答两个问题：**怎么判断"这条我看过了"**，以及**怎么判断"这条太旧了"**。
> 它们看起来是两件事，实际是同一个毛病：把已经知道的东西又占一次注意力预算。

## 1. 为什么必须做

实测两条：

| 测的东西 | 结果 |
|---|---|
| 同一天跑两次抓取 | 86 条条目 **完全相同**（Jaccard = 1.0） |
| 已抓内容里 published_at 已知的比例 | 200 条里只有 **51 条**（25%） |

第一条意味着：只要任务重跑一次，你看到的就是上一遍的原班人马。
第二条意味着：即使想做"旧文降权"，也有一大半条目连时间都不知道。

## 2. 去重分三层，现在三层都有

| 层 | 判据 | 在哪 | 确定性 |
|---|---|---|---|
| 同一 URL | 规范化后完全相同 | `tools/crawl.py` 的 `seen_urls`；`ingest/dedupe.py` 的 `SAME_URL` | 是 |
| 同一内容 | `content_digest`（sha256） | `ingest/dedupe.py` 的 `SAME_CONTENT` | 是 |
| 同一事件 | 锚点重合（见第 3 节） | `judgment/events.py` | 是 |
| 跨运行 | 已推送台账 | `store/repeat_guard.py` | 是 |

第三层是这轮新加的。前三层的区别不是"严格程度"，是**判据不同**：
前两层比字符串，第三层比"这件事本身"。

## 3. 事件去重：怎么判断"说的是同一件事"

### 3.1 锚点

从标题与前 400 字里抽三类：

| 类型 | 例子 | 可靠性 |
|---|---|---|
| 版本号（带数字的型号） | `V4.1`、`GPT-6`、`1017` | 高 |
| 专有名词（带大写的拉丁词） | `DeepSeek`、`Anthropic`、`MCP` | 中 |
| 稀有 CJK 片段（3–4 字，语料内少见） | `郑钦文` 这类 | 低 |
| 标题词集合（英文改写用） | `cyber verification program` | 中 |

**连写型号必须拆开**：`DeepSeek-V4.1-Flash-1017` 整体看是个版本号，
但里面的 `DeepSeek` 才是两条报道能对上的那个锚点。不拆，两条同一事件永远对不上。

### 3.2 判定规则（写死五条）

| # | 规则 | 对应形态 |
|---|---|---|
| 1 | 共同版本号 ≥ 2 | 同一个发布被两家写 |
| 2 | 共同版本号 ≥ 1 且共同专有名词 ≥ 1 | 「DeepSeek 发布 V4.1」与「V4.1 实测」 |
| 3 | 共同专有名词 ≥ 2 且标题相似度 ≥ 0.30 | 英文改写 |
| 4 | 稀有 CJK 片段 ≥ 2 且标题相似度 ≥ 0.35 | 中文媒体不写版本号的情形 |
| 5 | 标题词重合 ≥ 4 且词相似度 ≥ 0.5 | 英文媒体改写 |
| 6 | 其余一律分开 | —— |

### 3.3 精度优先，这是刻意选的

**并错两条不同的事，比漏并一对更糟**：用户会以为这两件事是一件事。
所以阈值取保守值，宁可分开。

还有一条硬约束：**只并跨源**。同一来源内部的近似不是重复，是连载——
实测把 `给电子音乐人的 74 个建议（59/60/61）` 并起来全是误判。

### 3.4 已知局限，别当成已解决

- **召回率没有验证。** 现有 316 条真实内容里，跨源事件簇是 **0 组**——
  不是因为算法准，是因为这批语料本身就没有重复事件（源选得散，各写各的）。
  真正的检验要等一个大新闻被所有媒体同时报道的那天。
- **中文改写到不写型号时抓不到。** 「DeepSeek 新模型发布」和「突发！超级性价比斩杀一切」
  之间没有共同锚点，这一对会被漏掉。要补只能上模型抽事件，那是另一件事。
- **传播性（transitivity）**：A≈B 且 B≈C 会把 A 和 C 并在一起，即使 A、C 同源。
  这符合"同一事件"的直觉，但也会放大一次误判的影响。

## 4. 时效：只降权，不加分

### 4.1 两条线要分开

| 线 | 用途 | 精度要求 | 现状 |
|---|---|---|---|
| `published_at`（契约字段） | 事实 | 必须带时区，否则记 UNKNOWN | 严格要求，不放松 |
| `judgment.recency.estimate()` | 降权 | 日精度够用 | 六种来源依次回退 |

**估计值不回填 `published_at`。** 契约说不知道就是不知道；
估计只用于"这条是不是两周前的旧闻"，且必须带上 `precision`。

### 4.2 取时间的顺序

1. meta 里明写的时间（`article:published_time` 等）
2. JSON-LD 的 `datePublished`
3. `<time datetime>` 语义标记
4. arXiv 编号里的年月（`2610.22350` → 2026 年 10 月，月精度）
5. URL 里的日期（`/2026/10/17/`、`/2026-10-17-`、`/2026/Oct/17/`）
6. 正文前 1500 字里的中文或英文日期
7. 都没有 → UNKNOWN

第 4 条是这轮最划算的一条：论文类来源（9 个）实测覆盖率从 **0% 直接到 100%**。

覆盖率变化：

| 语料 | 之前 | 现在 |
|---|---|---|
| 200 条媒体内容 | 25.5% | **28.5%** |
| 90 条混合内容 | 26.7% | **43.3%** |
| 6 条论文内容 | 0% | **100%** |

### 4.3 降权的形状

- ≤ 14 天：不降
- 14 → 60 天：线性从 0 到 0.08
- > 60 天：0.08 封顶
- **时间未知：不降权，只标记**

最后一条是刻意的：把"不知道"当成"很旧"和当成"很新"一样是编造。
未知的条目在终选包里会显示 `age=UNKNOWN`，由人来看。

### 4.4 为什么是"只降权"

政策 §4.2 写的是**「不因内容新鲜、有趣或容易获取就提高优先级」**。
这句话约束的是"新→加分"，不约束"旧→减分"。这两件事必须分开做：
加分会让系统追热点，减分只是把隔夜饭端下去。

## 5. 已推送台账：7 天窗口 + 重推闸门

### 5.1 规则（用户 2026-10-19 定）

| 情况 | 结果 |
|---|---|
| 没见过 | 放行 |
| 见过，且 < 7 天 | **压住**（REPEAT_WINDOW） |
| 见过，≥ 7 天，分数涨了 ≥ 0.10 且出现新锚点 | 放行（REPUSH_UPDATED） |
| 见过，≥ 7 天，其余任何情况 | **压住**（NO_PROGRESS） |

第三、四行合起来堵的就是那句话：**"没价值的信息，7 天之后不该又推一次"**。
窗口过期不等于放行，要放行必须同时满足"更值得看"和"有新进展"。

"有新进展"的可操作定义：这次出现了上次没有的锚点（新版本号、新日期、新数字）。
不用语义判断，因为语义判断没法复算。

### 5.2 实测

拿两条 HF 论文做样本，记进台账后复算：

```
2 天后   压住 item-f356485c60ee  REPEAT_WINDOW  age=2.7
11 天后  压住 item-f356485c60ee  NO_PROGRESS    age=11.7
```

第二条就是用户担心的情形：过了窗口，但因为没有新进展，仍然不推。

## 6. 怎么用

```powershell
# 过滤：把推过的压住
python tools/repeat_guard.py --items runs/crawl-<日期> --scores <打分行> \
    --ledger store/delivered.jsonl --out runs/crawl-<日期>/repeat.json

# 记账：这次真推出去的写进台账
python tools/repeat_guard.py --record --selection runs/agent/<日期>/selection.json \
    --items runs/crawl-<日期> --ledger store/delivered.jsonl
```

台账是 JSONL，一行一条，含 item_id / canonical_url / event_key / event_anchors / score / delivered_at。
存在本地 `store/delivered.jsonl`（已在 .gitignore 里），不进仓库。

## 7. 还缺什么

1. **台账已经接进交付环节。** `tools/final_digest.py` 默认在产出后自动记账
   （`--no-record` 可关），下次运行 `tools/repeat_guard.py` 就会压住这些条目。
   仍缺的一环是：**压住之后候选不够时怎么办**——现在只是放行更少，不做补位。
2. **事件召回的检验。** 需要等一次真实的大事件，看不同来源的报道有没有被并起来。
3. **时间未知仍是多数（约七成）。** 只能靠台账去重，不能靠降权。
4. **同源内的近似没有处理。** 系列连载与真重复混在一起，现在靠"只并跨源"回避。
